# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A small e-commerce REST API (Node.js + TypeScript, Express 5, PostgreSQL, Redis), built as a learning project. The
README (in Polish) holds the roadmap. Next up are production preparation, then Cart → Checkout → Payment (Stripe) →
Order. The guiding principle is to keep the architecture simple for a small shop but open to growth, without
overengineering.

## Commands

The package manager is pnpm.

```bash
docker compose up -d        # Postgres :5432, Redis :6379, Mailpit (SMTP :1025, UI :8025)
pnpm migrate                # apply migrations to dev DB (.env)
pnpm migrate:test           # create ecommerce_test DB if missing + apply migrations (.env.test)
pnpm dev                    # run API via tsx on :3000; Swagger at /api-docs
pnpm test                   # all tests (needs Postgres + Redis running and migrated test DB)
pnpm test -- src/__tests__/api/products.api.test.ts   # single file
pnpm test -- -t "should get a product by id"          # single test by name
npx tsc --noEmit            # type-check (no build/lint scripts are defined)
npx eslint .
```

`pnpm test` runs Jest with `--silent`, which hides `console.*` output. When debugging, run
`NODE_ENV=test NODE_OPTIONS=--experimental-vm-modules npx jest <file>` without `--silent`.

## Architecture

The request flow is routes → middleware → controller → service → repository → PostgreSQL. All wiring happens by hand in
**`src/dependency-injection.ts`**, the composition root. It builds the repositories, services, controllers, the Redis
client, multer and storage, and exports the routers that `src/app.ts` mounts. When you add a feature, register it there
and mount its router in `app.ts`.

Key conventions that span several files:

- **Repositories are stateless and take a `PoolClient` as the first argument of every method.** They never get a
  connection themselves. Each has an `*.interface.ts` and a `*-postgres.repository.ts` implementation.
- **Services own connections and transactions.** They depend on the `Database` interface
  (`src/database/database.interface.ts`, which has only `connect()`), not on `pg.Pool` directly. The service calls
  `pool.connect()`, runs `BEGIN`/`COMMIT`/`ROLLBACK` itself, and releases the client in `finally`. The same client is
  passed to every repository call inside the transaction. See `OrderService.createOrder` for the pattern.
- **Cache invalidation lives in services.** A single `RedisCache` instance (`productCache`) is shared by the product,
  product-variant-media and order services. Any mutation that affects product listings or stock calls
  `productCache.clear()` after commit. Behind the `Cache<T>` interface, `InMemoryCache` is an alternative
  implementation. The Redis URL is hard-coded to `localhost:6379`, and the app still starts if Redis is down.
- **Controllers** are classes whose handlers are arrow-function properties, so they can be passed to routes without
  binding. They validate input with plain predicate functions from `src/validators/` (e.g. `parseId`,
  `isValidPagination`, `isValidProductName`) and return 400 with `{ message }` themselves. They don't try/catch: Express
  5 forwards async rejections to the global error handler.
- **Errors**: domain errors extend `AppError(message, statusCode)` in `src/errors/`. The error handler in `app.ts` maps
  `AppError` to its status code, `entity.too.large` to 413, and everything else to 500. Every response body has the
  shape `{ message, ... }`.
- **Auth**: `authenticationMiddleware` verifies a Bearer JWT (its config comes from `JWT_*` env vars) and sets
  `req.user = { userId, email }`. Authorization is RBAC: `requirePermission(authorizationService, "resource:action")`
  checks the user → roles → permissions tables. Permission strings such as `products:create` must exist in
  `seed_data.sql`.
- **Routers** are factory functions (`createXRouter(controller, authorizationService, ...)`). The OpenAPI docs are
  generated by swagger-jsdoc from the `@openapi` JSDoc blocks in `src/routes/*.ts`, so update those blocks when you
  change endpoints.
- **Media uploads** use multer memory storage (10 MB limit) and go to the `Storage` interface, implemented by
  `LocalStorage` under `STORAGE_PATH` (default `./uploads`).
- Soft deletes are done with an `is_deleted` flag, and queries filter on `is_deleted = FALSE`.

## Module / TypeScript setup

- The project is ESM (`"type": "module"`, `module: nodenext`). **Relative and alias imports must use the `.js`
  extension** even for `.ts` files: `import { X } from "@/services/x.service.js"`.
- The `@/*` alias points to `src/*`. It works in tsx through tsconfig paths and in Jest through `moduleNameMapper`.
- The tsconfig is strict and also enables `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and
  `verbatimModuleSyntax`, so type-only imports must use `import type`.

## Database & migrations

- Migrations are numbered raw SQL files in `src/database/migrations/`. `migrate.ts` applies them in sorted filename
  order, one transaction per file, and records each in `schema_migrations`. **`seed_data.sql` sorts last and is applied
  as a migration too.**
- `src/database/db.ts` loads `.env.test` when `NODE_ENV=test`, otherwise `.env`.

## Tests

- Test files live in `src/__tests__/`: `api/` has supertest tests against the real app and DB, and the other folders
  hold unit tests for services, which use `jest.Mocked<...Interface>` repositories and a mock `Database` whose
  `connect()` returns a mock client. The cache tests sit next to their code in `src/cache/`.
- `src/database/test-setup.ts` runs before every test file. It **TRUNCATEs all tables and reloads `seed_data.sql` before
  all tests and after each test**. Tests run serially (`maxWorkers: 1`) because they share one DB. If you add a table,
  add it to the TRUNCATE list in `src/database/test-database.ts` unless a CASCADE from an existing table already covers
  it.
- API tests that import `app` must close Redis in `afterAll`: `await redisClient.close()` (import it from
  `dependency-injection.js`).
- Seed users log in with password `alamakota`: `alice@example.com` is a regular user and `bob@example.com` is an admin.
  Use `loginAsUser()` / `loginAsAdmin()` from `src/__test-helpers__/auth.ts`. The upload fixtures are in
  `src/__tests__/unit/services`.
